## 1. 목표

거래소 7곳의 시세로 기술적 지표를 각각 계산하고, **매수/매도 시그널과 거래소 합의도를
실시간으로** 보여주는 단일 페이지 대시보드.

성공 기준:

1. 페이지를 열면 3종목의 현재가·시그널 점수·등급이 즉시 보인다.
2. 각 시그널이 **왜** 그렇게 판정됐는지 근거 지표값이 함께 보인다.
3. 거래소들이 같은 방향을 가리키는지(합의도)가 숫자를 읽기 전에 보인다.
4. 체결이 일어나면 화면이 즉시 갱신된다.
5. 거래소 하나가 끊겨도 **그 거래소만** 강등되고 나머지는 실시간을 유지한다.
6. 어떤 거래소가 지표를 낼 수 없으면 그 사유가 화면에 드러난다.
7. 지표·시그널·집계 계산이 자동화된 테스트로 검증된다.

명시적 비목표(YAGNI): 로그인, 주문 실행, 백테스트, 알림 발송, 종목/거래소 추가 UI,
서버 사이드 저장.

### 2.1 거래소별 제약과 대응

거래소를 늘리면서 드러난 고유 함정을 기록으로 남긴다. 전부 실측으로 확인했다.

| 거래소 | 함정 | 대응 |
|---|---|---|
| 코인원 | 공개 API 가 **어떤 경로도 `access-control-allow-origin` 헤더를 주지 않는다**(ticker_new·chart·orderbook·구형 /ticker 모두). Node 의 fetch 는 CORS 를 무시하므로 서버 테스트만으로는 드러나지 않는다 | `browserRest = false` 로 표시하고 캔들 요청 대상에서 제외. 소켓은 CORS 대상이 아니라 정상이므로 **시세 전용**으로 다루고 화면에 사유를 적는다 |
| 코인베이스 | 4시간 granularity 미지원(`400 Unsupported granularity`). 캔들 필드가 `[시각, 저가, 고가, 시가, 종가]` 로 흔한 o,h,l,c 순서가 아니다. 시각이 초 단위 | 1시간봉을 4개씩 합성(`aggregateCandles`). 필드 순서는 픽스처 테스트로 고정 |
| 크라켄 | BTC 가 **XBT** 이고, 요청한 `XBTUSD` 가 응답에서 `XXBTZUSD` 로 정규화된다. 소켓 v2 는 또 `BTC/USD` 를 쓴다(표기가 셋). 공개 API 한도가 낮다 | 응답 키를 가정하지 않고 자산명 포함 여부로 되찾는다. 요청 간격을 600ms 로 벌린다 |
| 빗썸 | 일봉이 00:00 KST 에 시작해 업비트(09:00)와 다르다. 429 응답의 **본문이 비어 있다** | 일봉 지표 차이는 정상으로 두고 화면에 고지. `getJson` 이 `res.ok` 를 먼저 확인해 파싱 오류로 번지지 않게 한다 |
| 업비트·빗썸 | 프로토콜이 동일(빗썸이 업비트 API 를 복제) | `upbit-style.js` 공장으로 구현을 공유 |

### 2.2 어댑터 경계

어댑터는 모두 같은 인터페이스를 노출한다.

```js
{ id, name, quote, providesFx,
  symbolOf(coin),
  fetchTickers(coins), fetchCandles(coin, timeframeKey), fetchCandleSet(coins),
  openSocket(coins, { onTick, onOpen, onClose }),
  parseTicker(raw), parseCandles(raw)   // 순수 — 네트워크 없이 테스트한다
}
```

파싱을 순수 함수로 떼어내는 이유는 거래소 7곳의 응답 형태가 전부 다르고 그 변환이
이 프로젝트에서 **가장 깨지기 쉬운 지점**이기 때문이다. 고정 픽스처로 검증한다.

`browserRest: false` 인 어댑터는 브라우저에서 REST 를 쓸 수 없다는 뜻이다. 캔들 수집과
폴링 폴백 대상에서 빠지고, 화면에는 사유가 표시된다.

### 2.3 순수 코어 불변

거래소를 7곳으로 늘리는 동안 `indicators.js` 와 `signal.js` 는 **한 줄도 바꾸지 않았다.**
두 모듈은 정규화된 캔들 배열만 받으므로 데이터 출처와 무관하다. 이 불변성은
기존 36개 테스트가 그대로 통과하는 것으로 확인한다.

## 3. 데이터

### 3.1 엔드포인트

| 거래소 | 시세 | 캔들 |
|---|---|---|
| 업비트 | `/v1/ticker?markets=KRW-BTC,…,KRW-USDT` | `/v1/candles/{days, minutes/240, minutes/60}` |
| 빗썸 | 업비트와 동일 (`api.bithumb.com/v1`) | 업비트와 동일 |
| 코인원 | `/public/v2/ticker_new/KRW/{coin}` | `/public/v2/chart/KRW/{coin}?interval={1d,4h,1h}` — 브라우저에서는 차단 |
| 바이낸스 | `/api/v3/ticker/24hr?symbols=[…]` | `/api/v3/klines?interval={1d,4h,1h}` |
| Bybit | `/v5/market/tickers?category=spot&symbol=…` | `/v5/market/kline?interval={D,240,60}` |
| 코인베이스 | `/products/stats` (전 종목 한 번에) | `/products/{id}/candles?granularity={86400,3600}` |
| 크라켄 | `/0/public/Ticker?pair=XBTUSD,…` (한 번에) | `/0/public/OHLC?pair=…&interval={1440,240,60}` |

Bybit `tickers` 와 코인원 `ticker_new` 는 심볼을 하나씩만 받으므로 종목별로 호출한다.
코인베이스와 크라켄은 세 종목을 한 번에 받을 수 있어 호출을 아낀다.

### 3.2 WebSocket

| 거래소 | 주소 | 주의점 |
|---|---|---|
| 업비트 | `wss://api.upbit.com/websocket/v1` | 응답이 **바이너리 프레임**이다. `binaryType='arraybuffer'` + `TextDecoder` 없이는 메시지가 통째로 버려진다 |
| 바이낸스 | `wss://stream.binance.com:9443/stream?streams=…@ticker` | 종목별 소켓을 열지 않고 combined stream 하나로 묶는다. 포트가 9443 이다 |
| 빗썸 | `wss://ws-api.bithumb.com/websocket/v1` | 업비트와 같은 프로토콜 |
| 코인원 | `wss://stream.coinone.co.kr` | 구독을 **종목별로 따로** 보낸다. `response_type: DATA` 만 시세다 |
| Bybit | `wss://stream.bybit.com/v5/public/spot` | 스냅샷 뒤 **변경된 필드만** 델타로 올 수 있다. 심볼별 캐시에 병합해야 고가·저가가 사라지지 않는다. 20초마다 `{"op":"ping"}` 을 보내지 않으면 끊긴다 |
| 코인베이스 | `wss://ws-feed.exchange.coinbase.com` | `channels: ['ticker']` 구독 |
| 크라켄 | `wss://ws.kraken.com/v2` | 심볼 표기가 REST 와 다르다(`BTC/USD`). `data` 가 배열이다 |

업비트 소켓 구독에 `KRW-USDT` 를 함께 넣어 환율도 실시간으로 받는다.

### 3.3 호출 예산

가격은 소켓으로 오므로 REST 는 캔들에만 쓴다. 캔들을 받을 수 있는 거래소 6 × 종목 3 ×
주기 3 = **54회를 30초마다**(코인원은 제외). 거래소끼리는 병렬, 한 거래소 안에서는 직렬로
흘린다. 간격은 거래소별로 다르다 — 크라켄만 600ms, 나머지는 150ms.

**도착한 거래소를 그때그때 반영한다.** `Promise.all` 로 전부 기다리면 화면이 가장 느린
거래소에 묶인다. 크라켄 한 바퀴가 10초 가까이 걸려서, 거래소가 셋일 때는 2초라 보이지
않던 문제가 일곱이 되면서 **초기 화면이 13초 넘게 비는 회귀**로 드러났다. 소켓을 캔들보다
먼저 열고, 캔들 없이도 시세와 골격을 먼저 그린다(카드 첫 렌더 0.1초).

### 3.3.1 뉴스·심리 중계 (`serve.py`)

**뉴스 RSS 는 어느 매체도 CORS 를 열어주지 않는다.** CoinDesk·Cointelegraph·Decrypt·
블록미디어·TokenPost 를 모두 실측했고, CryptoCompare·CryptoPanic·CoinDesk 데이터 API 는
키를 요구하며 거래소 공지 API 는 404/302 다. 브라우저에서 직접 읽을 방법이 없다.

그래서 정적 파일 제공과 뉴스 중계를 한 파일(`serve.py`, 파이썬 표준 라이브러리만)로 합쳤다.

| 경로 | 내용 |
|---|---|
| `GET /` | 정적 파일 (기존 `http.server` 와 동일) |
| `GET /api/news` | RSS 5개 병합·최신순·5분 캐싱 |
| `GET /api/sentiment?coins=…` | 공포탐욕 + 트렌딩 + 종목별 투표, 5분 캐싱 |

심리 지표는 CORS 가 열려 있어 브라우저가 직접 부를 수도 있지만, 종목 6개 × CoinGecko 호출을
반복하면 무료 한도에 걸린다. 서버가 한 번 모아 캐싱하면 브라우저는 한 번만 부른다. 심볼→
CoinGecko id 매핑은 `/coins/list`(19,000종목·2MB)가 아니라 **시가총액 상위 500종목**으로
만든다 — 같은 심볼을 쓰는 사칭 토큰이 많아 순위가 높은 쪽을 채택해야 오선택이 없다.

**`serve.py` 없이 순수 정적 서버로 띄워도 화면은 그대로 동작해야 한다.** 두 엔드포인트가
실패하면 시장 심리 카테고리만 `데이터 없음` 으로 빠진다(코인원 CORS 처리와 같은 원칙).

보안 두 가지: 외부 RSS 를 파싱하므로 응답을 4MB 로 제한하고, **엔티티 선언(`<!DOCTYPE`·
`<!ENTITY`)이 보이면 파싱하지 않는다.** ElementTree 는 외부 엔티티를 가져오지 않으므로 XXE 로
파일을 읽는 경로는 없고, 남는 위험인 'billion laughs' 는 엔티티 선언이 반드시 필요하다.

### 3.4 정규화

캔들은 오래된→최신 순으로 맞추고 아래 형태로 통일한다. 업비트만 KST 문자열을 직접
주므로 그대로 쓰고, 나머지는 epoch 밀리초를 `Intl.DateTimeFormat('sv-SE')` 로 같은
형태로 만든다(이 로케일이 `YYYY-MM-DD HH:mm:ss` 를 내준다).

```js
{ time: Date, kst: '2026-09-03T09:00:00', open, high, low, close, volume }
```

티커는 `{ exchange, coin, price, changeRate, changePrice, direction, dayHigh, dayLow,
quoteVolume24h, at }` 로 통일한다. 거래소별 함정:

- 바이낸스 `priceChangePercent` 는 **퍼센트값**(0.127)이다. 100으로 나누지 않으면
  변동률이 127배로 부풀어 보인다. Bybit `price24hPcnt` 는 이미 비율이다.
- Bybit 은 변화 금액을 주지 않으므로 `lastPrice − prevPrice24h` 로 직접 만든다.
- 업비트 `high_price`/`low_price` 는 24시간 롤링이 아니라 **당일(09:00 KST 시작)** 기준이다.
  24시간 누적은 `acc_trade_price_24h` 하나뿐이다.

### 3.5 실시간 가격 반영

각 거래소의 **마지막 캔들 종가를 그 거래소의 현재가로 덮어써서** 지표를 다시 계산한다.
이걸 하지 않으면 캔들 갱신 주기(30초) 사이에 시그널이 굳고, 일봉은 하루 내내 전일
종가 기준 판정을 보여준다.

## 4. 시그널 산출 규칙

### 4.0 카테고리 계층 — 지표를 그냥 늘리지 않는 이유

지표 12개를 평탄 가중으로 합하면 **상관 높은 지표가 같은 근거를 여러 번 투표한다.**
MA·MACD·ADX 는 모두 추세를 보고, RSI·스토캐스틱은 모두 모멘텀을 본다. 그래서 계층을 둔다.

| 카테고리 | 지표 | 가중 |
|---|---|---|
| 추세 | MA20/60 · MACD · ADX/DMI | 1.2 |
| 모멘텀 | RSI · 스토캐스틱 · RSI 다이버전스 | 1.0 |
| 변동성 | 볼린저 %B · ATR 백분위 | 0.8 |
| 거래량 | 거래량비 · OBV 방향 | 0.7 |
| 실시간 수급 | 호가 불균형 · 체결강도 | 1.0 |
| 시장 심리 | 공포탐욕지수 · 뉴스 심리 · 커뮤니티 투표 · 검색 관심도 | 0.6 |

**카테고리 안에서는 단순 평균, 카테고리 사이에만 가중**을 둔다. 이러면 추세 지표를 셋
넣어도 추세가 세 표를 갖지 않는다.

`실시간 수급`은 `candleBased: false` 다 — 봉 주기 차원에 넣지 않는다. 호가와 체결은
캔들이 없으므로 일봉/4시간/1시간으로 반복할 대상이 아니다. 계산 순서는 이렇다.

```
캔들 지표 → 카테고리 4개 → 봉 주기 점수 → 거래소 점수 → 거래소 합의 점수 ─┐
                                                                          │
업비트 호가·체결 ───────────────→ 종목 단위 수급 점수 ────────────────────┤→ 최종 시그널
                                                                          │
뉴스·공포탐욕·투표·트렌드 ──────→ 종목 단위 심리 점수 ────────────────────┘
       캔들 3.7 : 수급 1.0 : 심리 0.6  (수급 18.9%, 심리 11.3%)
```

수급·심리를 봉 주기별 점수에 각각 더하면 같은 값이 세 번 세어진다. 캔들 계층을 끝까지
접은 뒤 마지막에 한 번만 얹는다(`aggregate.withExternal`).

### 4.0.1 ADX 동적 가중 — 이번 확장의 핵심

기존 구조의 가장 큰 결함은 **추세장에서 신호가 상쇄되는 것**이었다. `MA 정배열 +70` 과
`RSI 과매수 −80` 이 맞물려 중립으로 뭉개졌다(실제로 관측했다). 강한 추세에서 RSI 70 은
'비싸다'가 아니라 '계속 오른다'는 뜻인데 매도 표로 세어진 것이다.

ADX 가 추세의 **존재 여부**를 알려주므로 이것으로 카테고리 가중을 조정한다.

| 국면 | 조건 | 추세 | 모멘텀 | 변동성 |
|---|---|---|---|---|
| 추세장 | ADX ≥ 25 | ×1.5 | ×0.7 | ×0.8 |
| 전환 구간 | 20 ≤ ADX < 25 | ×1 | ×1 | ×1 |
| 횡보장 | ADX < 20 | ×0.6 | ×1.3 | ×1.2 |

효과는 테스트로 못 박았다. 추세 +70 · 모멘텀 −80 이라는 **같은 지표값**이 국면에 따라
`중립(1.8)` → `매수(28)` → `매도(−26.5)` 로 갈린다. 횡보장에서는 평균회귀를, 추세장에서는
추세추종을 신뢰하는 것이 정석이다.

### 4.1 지표별 판정 (각 −100 ~ +100, 양수 = 매수)

**RSI(14), 가중 1.0** — Wilder 평활

| 조건 | 점수 | 표시 |
|---|---|---|
| < 30 | +80 | 과매도 |
| 30 이상 ~ 45 미만 | +40 | 약세권 |
| 45 ~ 55 | 0 | 중립 |
| 55 초과 ~ 70 이하 | −40 | 강세권 |
| > 70 | −80 | 과매수 |

**MACD(12, 26, 9), 가중 1.2** — 크로스는 히스토그램 부호 전환으로 판정하고 최근 3봉 내에서만 유효하다.

| 조건 | 점수 | 표시 |
|---|---|---|
| 최근 3봉 내 골든크로스 | +90 | 골든크로스 |
| 최근 3봉 내 데드크로스 | −90 | 데드크로스 |
| 히스토그램 > 0 | +40 | 상승 모멘텀 |
| 히스토그램 < 0 | −40 | 하락 모멘텀 |
| 히스토그램 = 0 | 0 | 중립 |

**이동평균 MA20 / MA60, 가중 1.0**

| 조건 | 점수 | 표시 |
|---|---|---|
| 정배열 & 종가 > MA20 | +70 | 정배열 지지 |
| 정배열 & 종가 ≤ MA20 | +25 | 정배열 조정 |
| 역배열 & 종가 > MA20 | −25 | 역배열 반등 |
| 역배열 & 종가 ≤ MA20 | −70 | 역배열 약세 |

**볼린저밴드(20, 2σ) %B, 가중 0.8** — `%B = (종가 − 하단) / (상단 − 하단)`, 표준편차는 모집단 기준

| 조건 | 점수 | 표시 |
|---|---|---|
| %B < 0 | +80 | 하단 이탈 |
| 0 이상 ~ 0.2 미만 | +45 | 하단 근접 |
| 0.2 ~ 0.8 | 0 | 밴드 중앙 |
| 0.8 초과 ~ 1 이하 | −45 | 상단 근접 |
| %B > 1 | −80 | 상단 이탈 |

**거래량비(직전 완결봉 / 그 앞 20봉 평균), 가중 0.5**

| 조건 | 점수 | 표시 |
|---|---|---|
| 비율 ≥ 1.2 & 종가 > 시가 | +50 | 상승 거래량 동반 |
| 비율 ≥ 1.2 & 종가 ≤ 시가 | −50 | 하락 거래량 동반 |
| 그 외 | 0 | 평범 |

평균은 현재 봉을 **제외한** 직전 20봉으로 낸다. 현재 봉을 포함시키면 급증한 거래량이
스스로 기준선을 끌어올려 비율이 둔해진다.

거래량만 **직전 완결봉**으로 판정한다. 종가는 시점 값이라 진행 중인 봉의 값을 그대로
써도 완전한 데이터지만, 거래량은 봉 구간에 걸쳐 누적되는 값이다. 봉이 시작된 직후의
누적 거래량을 완결봉 20개의 평균과 비교하면 언제나 낮게 읽혀 지표가 구조적으로
망가진다(구현 중 실측: 일봉 시작 7분 뒤 `0.01배`).

**ADX/DMI(14)** — 강도와 방향을 나눠 잰다

ADX 는 **방향을 말하지 않는다.** 강한 상승과 강한 하락 모두 100 에 가까워지고 방향은
+DI/−DI 가 담당한다. 이것을 방향 지표로 쓰는 것이 대표적 오용이라 테스트로 고정했다.

방향은 `+DI − −DI` 에서 가져오고(격차 20 에서 포화), ADX 가 그 방향을 얼마나 세게 밀지
결정한다: ADX ≥ 25 → ×1, 20~25 → ×0.5, < 20 → ×0.2. 최대 ±80.

**스토캐스틱(14, 3)** — RSI 가 변화량의 평균을 보는 것과 달리 고저 범위 내 **위치**를 본다.

| 조건 | 점수 |
|---|---|
| %K < 20 & %K > %D | +80 (반전 시작) |
| %K < 20 & %K ≤ %D | +50 |
| 20 ~ 40 | +35 |
| 40 ~ 60 | 0 |
| 60 ~ 80 | −35 |
| %K > 80 & %K < %D | −80 |
| %K > 80 & %K ≥ %D | −50 |

**RSI 다이버전스** — 가격은 신고점인데 RSI 는 이전 고점보다 낮으면 상승 동력이 식은
것이다(−70). 반대는 +70. 없으면 0.

주의: `없음`(찾아봤지만 없다)과 `데이터 부족`(찾아볼 수 없다)은 다른 상태다. 봉이
`RSI 기간 + span×2 + 2` 개보다 적으면 판정하지 않는다 — 그러지 않으면 근거 없는 중립
표가 하나 생겨 전체 점수가 `판정 불가` 대신 `0` 으로 나온다.

**ATR(14) 백분위** — **방향 신호가 없다.** 변동성은 크기만 말하므로 거래량과 같은 방식으로
가격 방향과 짝지어야 뜻이 생긴다.

| 조건 | 점수 | 표시 |
|---|---|---|
| 백분위 ≥ 0.7 & 종가 > 시가 | +40 | 확장 · 상승 |
| 백분위 ≥ 0.7 & 종가 ≤ 시가 | −40 | 확장 · 하락 |
| 백분위 ≤ 0.3 | 0 | 변동성 압축 |
| 그 외 | 0 | 보통 |

절대값은 종목마다 자릿수가 달라 비교가 불가능하므로 가격으로 나눈 뒤 최근 100봉 안의
순위로 바꾼다.

**OBV 20봉 방향** — 누적 방향이 가격과 어긋나면 추세가 얇다.

| 조건 | 점수 |
|---|---|
| 가격·OBV 모두 상승 | +60 |
| 가격·OBV 모두 하락 | −60 |
| 어긋남 | ±30 |
| 변화 없음 | 0 |

### 4.1.1 실시간 수급 (캔들 무관)

업비트 WebSocket 의 `orderbook` · `trade` 스트림에서 직접 계산한다. 캔들 기반 지표는
본질적으로 지연 지표다 — RSI(14) 일봉은 14일치를 평활하므로 '지금 사도 되나'에 답하지
못한다. 이 두 지표가 화면에서 유일하게 진짜 실시간인 신호다.

**호가 불균형** = `(총매수잔량 − 총매도잔량) / 합계`, 30단계 기준. 이론상 ±1 까지
가능하지만 실전에서 ±0.3 이면 이미 극단이라 그 지점에서 포화시켜 ±100 으로 매핑한다.

**체결강도** = 최근 60초 `BID` 체결량 ÷ `ASK` 체결량 × 100. 100 이 균형이고 국내 거래소
화면의 그 값이다. ±40 에서 포화시켜 ±80 으로 매핑한다.

두 가지 안전장치를 둔다.

- 매도 체결이 0 이면 `Infinity` 가 화면까지 번지므로 999% 로 상한을 씌운다.
- **윈도우에 체결이 10건 미만이면 판정하지 않는다.** 60초에 두세 건뿐이면 비율이 3배든
  0.3배든 우연이다. 실제로 상한 999% 가 +80점(강한 매수)으로 계산되는 것을 관측했다.
  거래가 한산한 종목은 `체결 N건 (10건 필요)` 로 사유를 적는다.

### 4.1.2 시장 심리 (캔들 무관)

**공포탐욕지수** — 역추세로만 쓴다.

| 값 | 점수 | 표시 |
|---|---|---|
| < 25 | +60 | 극단적 공포 · 저가 기회 |
| 25 ~ 45 | +25 | 공포 |
| 45 ~ 55 | 0 | 중립 |
| 55 ~ 75 | −25 | 탐욕 |
| ≥ 75 | −60 | 극단적 탐욕 · 과열 주의 |

이 지수는 BTC 가격 모멘텀 25% + 변동성 25% 로 구성돼 이 화면의 추세·변동성 지표와
성분이 절반 겹친다. 방향 신호로 그대로 더하면 같은 정보를 두 번 세는 셈이다. 역추세로
쓰면 중복이 아니라 역발상 지표가 된다.

**뉴스 심리** — 한/영 키워드 사전(가중 −3~+3)의 합을 ±100 으로 눌러 담는다. 기사별 점수를
종목 언급 여부(종목 1.0 · 시장 전체 0.4)와 최신성으로 가중해 합산한다.

세 가지 구현 세부가 결과를 크게 바꾼다.

- **긴 표현을 먼저 검사하고 차지한 글자 구간을 소비 처리한다.** 그러지 않으면 `상장폐지`(−3)와
  `상장`(+3)이 같은 글자에 동시에 걸려 최악의 뉴스가 0점이 된다(실측 확인). `숏 청산`(+2) 역시
  일반 `청산`(−2)보다 먼저 걸려야 숏스퀴즈를 하락으로 오독하지 않는다.
- **부정어 뒤 12자 안에 해소 표현이 오면 무효로 본다.** `해소·완화·진정·끝났·종료·탈출` 등.
  `약세장 끝났다` 가 부정으로 읽히는 것을 실제 화면에서 잡았다.
- **분모를 `max(가중합, 1)` 로 둔다.** 그냥 가중 평균이면 분모가 가중을 상쇄해 기사가 한 건일
  때 최신성이 아무 효과가 없다 — 20시간 전 기사가 방금 나온 기사와 같은 점수를 냈다.
  최신성은 상대 비중이 아니라 크기를 줄여야 한다.

**커뮤니티 투표** — CoinGecko 상승 투표 비율. 분석이 아니라 인기 투표이므로 ±30 으로 묶는다.

**검색 관심도** — 트렌딩 진입 여부 × 24시간 방향. 관심이 몰린다는 사실만으로는 방향을 모르므로
ATR·거래량과 같은 원칙으로 가격 방향과 짝짓는다(±30).

**종목 매칭** — 제목에 한글명이나 심볼이 있으면 그 종목 기사로 본다. 심볼은 단어 경계를 봐야
한다(`ETHOS` 가 `ETH` 로 걸리면 오탐이 쏟아진다). 다만 `BTCUSD` 처럼 알려진 견적 접미사가
붙은 표기는 같은 종목이므로 예외로 허용한다.

> **키워드 감성의 한계를 분명히 한다.** 브라우저에서 언어 모델을 돌릴 수 없어 사전 방식이고,
> 사전은 문맥을 오해한다. 그래서 (1) 가중을 가장 낮게(0.6) 두고 (2) 부정 해소를 처리하고
> (3) 걸린 키워드와 헤드라인을 화면에 그대로 보여준다. 실제로 위의 오독 두 건은 헤드라인을
> 띄워 두었기 때문에 잡혔다. 정확한 뉴스 해석이 필요하면 LLM API 를 붙이는 별도 작업이다.

### 4.1.3 종목별 탐욕지수 (표시 전용)

alternative.me 의 공포탐욕지수는 **BTC 기준 시장 전체 값 하나**뿐이라 리플 카드에도
이더리움 카드에도 같은 숫자가 찍힌다. 종목 차이를 볼 수 없다.

그 산출 방식을 따라 종목별 지수를 만든다. 원 지수의 성분 중 설문(15%)과 도미넌스(10%)는
종목별로 만들 수 없어 제외하고 남은 성분을 재정규화했다.

| 성분 | 가중 | 데이터 | 매핑 |
|---|---|---|---|
| 모멘텀 | 35% | RSI(14) 일봉 | 그대로 (이미 0~100) |
| 변동성 | 25% | ATR 백분위 | **100 − 백분위×100 (역방향)** |
| 거래량 | 20% | 거래량비(직전 완결봉) | 0.5배↓ = 0 · 1배 = 50 · 2배↑ = 100 |
| 소셜 | 12% | CoinGecko 상승 투표% | 그대로 |
| 관심도 | 8% | 검색 상위 진입 | 진입 75 · 아님 45 |

변동성을 역방향으로 넣는 것이 핵심이다. 원 지수도 '이례적 변동성은 공포' 로 보므로
그대로 넣으면 급락장이 탐욕으로 읽힌다.

등급 구간은 원 지수와 같다: `0~24 극단적 공포 · 25~49 공포 · 50~74 탐욕 · 75~100 극단적 탐욕`.
없는 성분은 분모에서도 빠져 남은 성분끼리 재정규화되므로, 캔들만 있어도 지수가 나온다.

> **점수에는 반영하지 않는다.** 이 지수의 재료가 이미 시그널 점수에 들어간 지표들이므로
> 다시 넣으면 같은 정보를 두 번 세게 된다. USDT 기준 괴리를 점수에서 뺀 것과 같은 이유다.
> 화면에는 시장 지수와 나란히 두어 '시장은 탐욕인데 이 종목만 공포' 라는 어긋남을 드러내는
> 용도로만 쓴다(실측: 시장 65 탐욕 · BTC 59 탐욕 · XRP 37 공포).

구현 세부 하나: 표시 문자열을 파싱하지 않고 **캔들에서 다시 계산한다.** `evaluateTimeframe` 이
이미 RSI·ATR 을 계산하지만 결과가 `"62.8"` 같은 표시용 문자열로만 남아 있어, 파싱해 쓰면
표시 형식이 바뀔 때 조용히 깨진다. 재계산 비용은 밀리초 단위다.

### 4.2 봉 주기 점수

`카테고리 점수 = 계산 가능한 지표의 단순 평균`
`봉 주기 점수 = Σ(카테고리점수 × 가중 × ADX조정) / Σ(가중 × ADX조정)`

계산 불가한 지표·카테고리는 **분모에서도 제외**하고 `데이터 부족`으로 표시한다.

### 4.3 거래소 점수

봉 주기 가중: **일봉 0.5 / 4시간 0.3 / 1시간 0.2**. 값이 있는 주기만으로 재정규화한다.

### 4.4 시그널 점수와 합의도 (거래소 집계)

두 값은 **서로 다른 것을 잰다.** 나란히 두어야 정보가 보존된다.

| 값 | 정의 |
|---|---|
| 시그널 점수 | 지표를 낸 거래소 점수의 **등가중 평균** |
| 합의 방향·개수 | 거래소별 방향(매수/중립/매도)의 **최다값과 그 개수** |

등가중을 쓰는 이유: 거래소 점수들은 같은 시장을 여러 번 측정한 값이고, 한쪽을 더
신뢰할 근거가 없을 때 측정치를 합치는 표준 방식이 등가중이다. 거래대금으로 가중하면
바이낸스가 사실상 단독 결정하게 되어 합의도라는 개념 자체가 무의미해진다.

합의 방향을 평균에서 파생시키지 않는 이유: `45 / 40 / −30` 의 평균은 18.3(중립)인데,
평균에서 방향을 뽑으면 두 거래소가 매수를 가리켰다는 사실이 사라진다. **이견이 상쇄로
위장되는 셈이다.** 최다값을 쓰면 `점수 +18 중립 · 합의 2/3 매수 우세` 로 두 사실이
모두 남는다.

최다 방향이 둘 이상으로 갈리면(각 1표씩) 다수라고 부를 수 없으므로 평균 방향으로 적고
`이견` 으로 표시한다.

합의 라벨: `완전 일치`(3/3) · `다수 일치`(2/3) · `이견` · `단독 판정`(거래소 1곳만 생존) ·
`데이터 없음`.

### 4.5 등급

| 점수 | 등급 |
|---|---|
| ≥ +50 | 강력매수 |
| +20 이상 ~ +50 미만 | 매수 |
| −20 초과 ~ +20 미만 | 중립 |
| −50 초과 ~ −20 이하 | 매도 |
| ≤ −50 | 강력매도 |

±20 은 중립이 아니라 **행동 쪽으로 붙는다.** 경계에 정확히 걸친 점수를 '아무 신호 없음'
으로 버리지 않기 위한 선택이며, 한 방향 비교만으로는 표현되지 않는다.

### 4.6 USDT 기준 괴리 (점수에 반영하지 않음)

```
괴리 = 업비트KRW / (바이낸스USDT × 업비트 KRW-USDT) − 1
```

업비트에 `KRW-USDT` 마켓이 있으므로 외부 환율 API 없이 시장이 매기는 환율을 그대로 쓴다.

**흔히 말하는 '김치 프리미엄'과 다른 값이다.** 그쪽은 은행 USD/KRW 환율을 쓰기 때문에
USDT 자체의 프리미엄까지 포함해 보통 1~3% 로 나온다. 여기서 재는 것은 그 성분을 걷어낸
거래소 사이의 순수 가격 차이라 평소 0% 근처에 머문다(실측 ±0.06%). 같은 이름을 쓰면
2% 를 기대하고 0.03% 를 보게 되므로 화면에도 `USDT 기준 괴리` 로 적는다.

시그널 점수에 넣지 않는다. 의미가 국면에 따라 뒤집히고, 점수에 섞으면 가격에 이미
반영된 정보를 이중으로 세게 된다.

## 4.7 종목 선택 (업비트 기준)

업비트 KRW 마켓 287종목에서 고른다. 업비트를 기준으로 삼는 이유는 원화 마켓이 실제 거래
대상이고, `KRW-BTC` 처럼 종목 코드에 자산명이 그대로 담겨 다른 거래소 심볼로 옮기기 쉽기
때문이다.

- 목록은 `/v1/market/all?isDetails=true` 로 한 번만 받아 캐시한다. 상장·폐지는 드물다.
- 한글명·심볼 어느 쪽으로도 검색된다. 업비트가 지정한 **투자주의** 종목은 배지로 드러낸다.
- 선택은 `localStorage` 에 저장한다. 저장 형식이 깨졌거나 저장이 막혀도(사생활 보호 모드)
  화면은 기본 종목으로 계속 뜬다.
- **상한 6종목.** 거래소 7 × 종목 N × 주기 3 이 30초마다 돈다. 한도가 가장 낮은 크라켄은
  요청 간격이 600ms 라 N=6 이면 한 바퀴 10.8초, N=20 이면 36초로 갱신 주기를 넘긴다.
- 마지막 한 종목은 지우지 않는다. 빈 화면은 고장으로 보인다.
- 알트코인은 해외 거래소에 없는 경우가 많다. 카드에 `N/6 거래소` 를 표시해 '합의 2/2 완전
  일치'가 근거 두 곳뿐이라는 사실을 감추지 않는다.

종목이 바뀌면 소켓 구독과 캔들을 모두 간다. **순서가 중요하다** — 먼저 구독을 바꿔 시세가
흐르게 하고 캔들은 뒤에서 채운다. 캔들을 먼저 기다리면 가장 느린 거래소 때문에 화면이
10초 넘게 멈춘다. 빠진 종목의 체결 누적·전환 이력·캔들·티커는 함께 버린다(다시 담았을 때
옛 체결이 섞이지 않게).

## 4.8 전환 기록

종목별 이전 등급을 들고 있다가 **바뀔 때만** 기록한다(최대 50건). 순간 값만 보여주는
화면에서는 방금 매수로 돌아섰는지, 원래 매수였는지 구분할 수 없다.

각 기록에 그 시점 **기여도 상위 지표 2개**(절대값 기준)를 남겨 왜 전환됐는지 사후에 확인할
수 있게 한다. `판정 불가` 로 바뀌는 것은 전환으로 세지 않는다 — 연결이 끊겨 데이터가 빈
것과 시그널이 바뀐 것은 다른 사건이다.

### 5.1 시그니처 요소 — 공유 축 게이지

카드마다 −100 ~ +100 수평 축을 두고 중앙 0에 눈금을 찍는다. 시그널 점수는 굵은 마커로,
거래소들은 같은 축에 얇은 마커로(거래소별 색) 얹는다.

의도: 원형 게이지 세 개를 나열하면 각 값은 읽히지만 **합의/이견은 읽히지 않는다.**
축을 공유시키면 마커가 모여 있으면 합의, 흩어져 있으면 이견이라는 사실이 숫자를 읽기
전에 보인다. 구조가 정보를 담게 하는 것이 이 화면의 핵심 장치다.

### 5.2 색과 타이포

- 배경 `#0d0e12`, 패널 `#15171d`, 실선 `#232733`, 본문 `#e8eaf0`, 보조 `#7c8395`
- 매수·상승 `#f0473e`(빨강), 매도·하락 `#2f7cf6`(파랑) — 한국 시장 관례
- 거래소 마커는 커스텀 속성 `--ex` 하나로만 정의한다(게이지·카드 셀·격자 점이 같은 값을 쓴다)
- 연결 상태: 실시간 `#33c76a`, 폴링·연결 중 `#e3b341`, 중단은 파랑
- 폰트는 시스템 폰트만 사용(CDN 의존 금지). 수치는 `tabular-nums` 고정폭으로 갱신 시
  자리가 흔들리지 않게 한다.

### 5.3 시세 표기

자릿수는 **견적 통화와 가격대를 함께** 봐야 정해진다. 크기만으로 판단하면 XRP
1.3463 USDT 가 `1.35` 로 잘려 소수 넷째 자리의 움직임이 사라진다. 반대로 원화는
1,000원 이상에서 정수로 호가되니 소수점을 붙이면 없는 정밀도를 꾸며내는 셈이 된다.

| 견적 | 규칙 |
|---|---|
| KRW | ≥1,000 → 정수 · ≥100 → 1자리 · ≥1 → 2자리 · 그 외 4자리 |
| USDT/USD | ≥1,000 → 2자리 · ≥10 → 3자리 · ≥1 → 4자리 · 그 외 6자리 |

차트 가격축도 같은 원칙을 따른다. **억·만 단위는 원화 전용**이다 — USDT 축에 쓰면
BTC 77,098 이 `8만` 으로 찍혀 완전히 다른 뜻이 된다.

### 5.3.1 점수를 분해해 보여주는 이유

카드에 `시그널 +18점` 과 `6/6 완전 일치 · 캔들 중립` 이 나란히 있으면 모순처럼 읽힌다.
합의는 **거래소들의 캔들 판정**이고 +18점은 거기에 **업비트 단독 수급 신호**를 얹은 값이다.
수급은 한 거래소에서만 오므로 애초에 거래소 간 합의에 참여할 수 없다. 그래서 점수 옆에
`캔들 −1 · 수급 +90` 을 적어 산술을 드러낸다.

### 5.4 상호작용

- 헤더 `종목 N/6` → 선택 패널 열기·닫기, 검색해서 추가, 칩·카드 × 로 제거
- 카드 클릭 → 차트·격자·상세가 그 종목으로
- 거래소 탭 / 봉 주기 탭 전환, 격자 행 클릭으로도 거래소 선택
- 차트 `보조` 탭 → 서브차트를 RSI·MACD·스토캐스틱 중에서 고른다. RSI·스토캐스틱은 0~100
  고정 축을 공유하고 MACD 만 값 범위가 종목마다 달라 자체 축척을 쓴다
- 헤더 `일시정지` → 소켓을 끊고 캔들 조회를 멈춘다. 화면의 값은 마지막 수신 시점 그대로 남는다
- 차트 호버 → 십자선 + 해당 봉의 시/고/저/종·거래량 툴팁
- 체결이 오면 가격에 짧은 배경 플래시(`prefers-reduced-motion` 에서는 끔)
- 키보드 포커스 링 표시, 모바일 폭까지 반응형

### 5.4.1 주기 작업 제어

주기 작업에 이름 있는 핸들을 두고 세 경로에서 제어한다.

| 계기 | 동작 |
|---|---|
| `일시정지` 버튼 | 소켓 7본 정리 + 캔들·뉴스 조회 중단. 다시 누르면 재연결하고 즉시 1회 갱신 |
| 탭 숨김(`visibilitychange`) | **캔들 조회만** 중단. 복귀 시 즉시 1회 조회 후 주기 재개 |
| 페이지 이탈(`pagehide`) | 소켓과 모든 타이머 정리 |

탭 숨김에서 소켓을 끊지 않는 이유가 있다. 끊으면 복귀할 때 7곳을 다시 연결하는 지연이
생기고, 체결 누적이 비어 체결강도가 '표본 부족' 으로 떨어진다. 반면 캔들 조회는 30초마다
54회라 백그라운드에서 계속 돌 이유가 없다.

이 제어가 없던 동안 `realtime.stop()` 은 정의만 되어 있고 어디서도 호출되지 않았다 —
탭을 백그라운드에 두면 소켓 7본과 캔들 폴링이 무한히 돌았다.

### 5.5 렌더 스케줄

체결은 초당 수십 건까지 몰린다. 틱마다 27개 조합을 재계산하고 DOM 을 다시 만들면
화면이 멈추므로 주기를 나눠 묶는다.

| 대상 | 주기 |
|---|---|
| 지표 재계산 + 카드·격자·상세 | 400ms |
| 차트 재렌더(노드가 많다) | 2초 |
| 캔들 재조회 | 30초 |

## 6. 오류 처리

| 상황 | 동작 |
|---|---|
| REST 실패 / 5xx / 429 | 지수 백오프(400 → 800 → 1600ms) 최대 3회 재시도 |
| 4xx(잘못된 심볼 등) | 재시도하지 않고 즉시 포기 |
| 캔들 일부 실패 | **화면을 비우지 않는다.** 그 칸의 이전 캔들을 유지하고 배너로 알린다 |
| 소켓 끊김 | 지수 백오프로 재연결(상한 30초) |
| 소켓 3회 연속 실패 | **그 거래소만** REST 폴링(5초)으로 강등. 60초마다 소켓 복귀 시도 |
| 소켓 복귀 | 폴백 폴링을 멈춘다(둘을 함께 돌리면 호출만 낭비된다) |
| 캔들 부족 | 해당 지표만 `데이터 부족`, 가중 평균에서 제외 |

강등이 거래소 단위인 것이 핵심이다. Bybit 소켓이 죽었다고 전체를 폴링으로 내리면
살아 있는 두 곳의 실시간성을 함께 버리게 된다. 헤더의 거래소별 상태 칩으로 지금 보는
값의 출처가 실시간인지 폴링인지 드러낸다.

### 7.1 브라우저 검증 방법 (개발 환경)

Playwright 번들 Chromium 이 `~/.cache/ms-playwright/chromium-1234/chrome-linux/chrome`
에 있고 한글 폰트를 설치했으므로 헤드리스로 실제 렌더링을 확인할 수 있다. 이 환경의
함정 네 가지를 기록으로 남긴다.

- **최소 창 폭이 약 500px 이다.** `--window-size=390` 을 줘도 뷰포트는 500px 이고
  스크린샷만 잘린다. 좁은 화면은 폭 390px `iframe` 으로 감싼 프로브 페이지로 검증한다.
- **콘솔 접근이 없다.** 계산된 레이아웃 값이나 상호작용 결과를 확인하려면 측정 결과를
  `document.title` 이나 `<pre>` 에 써넣고 `--dump-dom` 으로 회수한다.
- **`--virtual-time-budget` 은 타이머만 앞으로 감고 실제 소켓 I/O 를 기다리지 않는다.**
  이 때문에 정상 동작하는 WebSocket 이 `연결 중` 으로 멈춘 것처럼 보인다. 실시간을
  검증하려면 **13초 뒤에 응답하는 이미지**를 페이지에 넣어 `load` 이벤트를 실제 시간
  만큼 붙잡아 둔다.
- **REST 폴백 경로를 일부러 태우는 방법**: 모듈 스크립트보다 먼저 실행되는 인라인
  스크립트에서 `window.WebSocket = undefined` 로 지우면 강등 로직과 렌더 파이프라인을
  한 번에 검증할 수 있다.

### 7.2 WebSocket 을 Node 에서 검증하기

Node 20 은 `--experimental-websocket` 플래그로 전역 `WebSocket` 을 제공한다. 어댑터가
전역 `WebSocket` 만 쓰므로, 브라우저 없이 실제 소켓 연결·구독·파싱을 검증할 수 있다.
가상 시간이 개입하지 않아 브라우저보다 확실한 검증 경로다.

```bash
node --experimental-websocket <스크립트>   # openSocket 을 직접 호출해 첫 틱을 확인
```

### 7.3 구현 중 실제로 잡은 결함

같은 계열의 실수를 반복하지 않기 위한 기록.

1. **빈 경고 배너가 늘 보였다** — `hidden` 속성은 UA 스타일시트의 `display:none` 으로
   동작하는데 `.banner { display: flex }` 가 이를 덮었다. `[hidden] { display: none !important }`
   를 전역으로 깐다.
2. **모바일에서 카드가 뷰포트를 넘쳤다** — 차트 SVG 의 고유 폭이 그리드 컬럼의
   min-content 로 되먹임되어 컬럼이 줄어들 수 없었다. `main` 에 `minmax(0, 1fr)`,
   카드에 `min-width: 0`.
3. **시계가 `9시 0분 3초` 로 표시됐다** — `ko-KR` 은 `hour12:false` 로도 풀어 쓴다.
   `en-GB` 패턴으로 `09:00:03` 을 얻는다.
4. **시간축 첫 라벨이 잘렸다** — 가운데 정렬 라벨은 좌우 끝에서 잘린다. 양 끝은
   `text-anchor` 를 `start`/`end` 로 바꾼다.
5. **가격축에 `1.208억` 과 `99,322,442` 가 섞였다** — 눈금마다 단위를 따로 고르면 축 내
   비교가 불가능하다. 축 전체의 최대값으로 포맷터를 한 번 정한다.
6. **거래량비가 `0.01배` 로 읽혔다** — 4.1절의 진행 중 봉 문제.
7. **합의 방향을 평균에서 파생시켰다** — 4.4절. 이견이 상쇄로 위장됐다.
8. **XRP 가격이 `1.35` 로 잘렸다** — 5.3절. 자릿수가 견적 통화를 몰랐다.
9. **USDT 축에 억·만 단위가 쓰일 수 있었다** — 5.3절. 원화 전용 단위를 통화 무관하게
   적용했다.
10. **'김치 프리미엄' 이라는 이름이 계산 내용과 달랐다** — 4.6절.
11. **초기 화면이 13초 넘게 비었다** — `await loadCandles()` 가 소켓 연결보다 앞에 있어
    가장 느린 거래소(크라켄)를 기다렸다. 거래소가 셋일 때는 2초라 보이지 않았다.
    소켓을 먼저 열고 캔들은 도착하는 대로 반영하도록 순서를 바꿨다(첫 렌더 0.1초).
12. **코인원이 가격은 나오는데 지표만 비었다** — REST 가 CORS 헤더를 주지 않아 브라우저가
    차단했다. Node 검증은 통과했으므로 **브라우저에서만 드러나는 결함**이었다. 2.1절.
13. **`parseTicker` 가 어댑터마다 다른 것을 뜻했다** — 인터페이스 계약 테스트가 잡았다.
14. **캔들 3개로도 다이버전스가 '없음 0점'을 냈다** — 표본이 없는데 단정해서 전체 점수가
    `판정 불가` 대신 `0(중립)` 으로 나왔다. 4.1절.
15. **체결강도 999% 가 +80점을 냈다** — 매도 체결 0건이면 상한이 걸리는데, 표본이 몇 건인지
    보지 않았다. 최소 10건을 요구하도록 고쳤다. 4.1.1절. 14번과 같은 계열의 결함이다.
17. **`상장폐지` 기사가 0점으로 읽혔다** — `상장폐지`(−3)와 `상장`(+3)이 같은 글자에 동시에
    매칭돼 상쇄됐다. 긴 표현을 먼저 검사하고 차지한 구간을 소비 처리해 고쳤다. 4.1.2절.
18. **`숏 청산`을 하락으로 셌다** — 숏스퀴즈는 상승 신호다. 방향이 정해진 표현을 사전에
    추가했다. 17번과 같은 처방으로 함께 해결됐다.
19. **`약세장 끝났다` 가 부정으로 읽혔다** — 해소 표현 목록에 `끝났·종료·탈출` 이 없었다.
    **헤드라인을 화면에 띄워 둔 덕에 잡혔다** — 점수만 내놓으면 영원히 안 보이는 종류다.
20. **뉴스 최신성 가중이 아무 효과가 없었다** — 가중 평균의 분모가 가중을 상쇄해 20시간 전
    기사가 방금 나온 기사와 같은 점수를 냈다. 4.1.2절.
21. **탐욕지수 거래량 성분이 세 종목 모두 0 이었다** — 진행 중인 일봉의 누적 거래량을
    완결봉 20개 평균과 비교했다. `signal.js` 에서 **이미 고치고 문서에 기록해 둔 함정을
    새 파일에서 다시 밟았다**(6번 항목과 같은 결함). 같은 계열의 실수가 반복되는 지점이라
    거래량을 쓰는 모든 곳에서 '직전 완결봉' 을 먼저 확인해야 한다.
22. **CoinDesk RSS 가 308 로 실패했다** — 파이썬 3.9 의 `urllib` 은 301·302·303·307 만
    따라가고 308 은 3.11 에서 추가됐다. 핸들러 등록만으로는 부족하고 `redirect_request` 가
    코드 목록을 다시 검사하므로 308 을 307 로 바꿔 넘겨야 한다.
16. **테스트 픽스처가 지표 정의를 오해했다** — (가) 고가를 고정한 '지그재그'는 `+DM` 이
    발생하지 않아 ADX 100 이 나왔다. (나) RSI 는 기울기를 보지 않으므로 하락 없이 오르기만
    하면 `+3/봉`이든 `+1.4/봉`이든 100 이다 — 다이버전스를 만들려면 되돌림 봉을 섞어야 한다.
    지표 정의를 정확히 이해하지 않으면 테스트 데이터부터 틀린다.
